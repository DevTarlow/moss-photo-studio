# Muse API notes

Moss Photo Studio was built against the Meta Muse image API described by the product brief. The implementation is deliberately conservative about the request surface and very explicit about the cases the documentation does not settle.

## Endpoints used

| Purpose | Request |
| --- | --- |
| Test a key | `GET https://api.meta.ai/v1/models` |
| Image Generator | `POST https://api.meta.ai/v1/images/generations` |
| Edit or make a version | `POST https://api.meta.ai/v1/images/edits` |

The app uses only these image endpoints. It does not call a text or chat model, and it does not use the SAM segmentation endpoint.

Every request has `Authorization: Bearer <key>`, `Content-Type: application/json`, `Accept: application/json`, and an `x-request-id` generated by the app. The model is `muse-image-1.0`.

Edits send source images as data URLs:

```json
{
  "model": "muse-image-1.0",
  "prompt": "...",
  "images": [{ "image_url": "data:image/webp;base64,..." }],
  "size": "1024x1024",
  "response_format": "b64_json",
  "output_format": "webp",
  "reasoning_strength": "high",
  "tool_enablement": { "enable_shell": false },
  "user": "install-id"
}
```

Edits omit `n`. Generations include `n` with the requested count. Neither endpoint sends a moderation field, because the brief does not define one and an invented field would turn every request into a 400. No `output_compression` is sent. The seller selects WebP, JPEG, or PNG and the format is the request's `output_format`.

`size` is exactly one of:

- `1024x1024`
- `1024x1536`
- `1536x1024`

The app never calculates a custom width and height for the model. An imported source with a different aspect ratio is sent as normalized, and the selected shape is only a request hint; the source is not cropped by the app yet. The original import is untouched. A center-crop preview and crop before the request are planned with the product-workspace work.

## Cost

`src/shared/cost.ts` is the only place that knows the price:

```ts
// Meta Model API price, checked 2026-11-05.
export const CENTS_PER_IMAGE = 1
```

The brief specified **$0.01 per returned image**. The app shows prices with `usd()`. A four-image Create is `$0.04`. A one-image retry is `$0.01`. The app does not keep a second copy of the rate in the interface, in prompts, or in the job copy.

The actual charge recorded for a response is `returnedCount` times the rate. A response that contains more images than requested still bills every returned image, even though the extra images beyond `n` are discarded. A request that timed out is recorded with zero counted cost plus an uncertain-billing flag. The ledger shows `Unknown`, the CSV leaves the cost blank, and monthly totals do not count it. A refusal or a response with zero images records `$0.00`. Usage totals use the recorded cost, not an estimate.

## Response handling

A successful response is expected to contain:

```json
{
  "created": 1234567890,
  "data": [{ "b64_json": "...", "revised_prompt": "..." }],
  "output_format": "webp",
  "usage": { "input_tokens": 10, "output_tokens": 20, "total_tokens": 30 }
}
```

Rules:

- `data` must be an array.
- Entries without a non-empty `b64_json` are skipped.
- If none survive, the result is `provider_error` with zero returned images.
- Only the first `n` images are written. `returnedCount` remains the full number decoded.
- `output_format` wins over the requested format when it is one of `webp`, `jpeg`, or `png`.
- `revised_prompt`, `usage`, and `request_id` are parsed. The queue currently stores `revised_prompt` as null and keeps the usage totals in the job state; they are not persisted as a separate row. The interface does not show revised prompts.
- No content type header is trusted for decoding. The bytes are decoded, then validated and normalised by sharp.

## Error handling

| Status or condition | Code | Retried automatically | Recorded cost |
| --- | --- | --- | --- |
| 401 | `invalid_key` | No | `$0.00` |
| 402 | `billing` | No | `$0.00` |
| 403 | `forbidden` | No | `$0.00` |
| 404 | `misconfigured` | No | `$0.00` |
| 429 | `rate_limited` | Yes, up to three attempts | `$0.00` counted, ledger Unknown if it still fails |
| 5xx | `provider_error` | No | `$0.00` counted, ledger Unknown |
| 400 with a content-policy code | `content_policy` | No | `$0.00` |
| 400 with `unsupported_parameter` | `app_bug` | No | `$0.00` |
| Other 400 | `invalid_request` | No | `$0.00` |
| Fetch throws, including timeout and refused connection | `network` | No | unknown, not counted |
| Caller aborts | `aborted` | No | `$0.00` because the response never arrived |
| 200 without usable images | `provider_error` | No | `$0.00` counted, ledger Unknown |

The `network` code is also the timeout code. Its interface copy is the approved timeout sentence. The client aborts the request when the app's 300 second timeout fires, but the response is not seen, so the app records no cost and marks the billing unknown. Aborting the local socket does not undo a charge Meta may already have made.

Rate limiting:

- Only 429 is retried.
- The client attempts three times total, then returns `rate_limited`.
- It honours `Retry-After` in seconds or HTTP-date form.
- Without the header it waits 500 ms then 1000 ms plus 0 through 199 ms jitter.
- While waiting, the job item says **Waiting for Meta**.

The app deliberately does not retry 401, 402, 403, policy refusals, 5xx, or malformed responses. The seller can choose **Try Again** manually. A refusal must never be retried automatically.

## Reference order

The Image Generator can send up to three references: product, person, scene. The request's `images` array is in that order and the prompt names the indices explicitly (`@Image1` product, `@Image2` person when present, then the scene). A three-reference edit was verified live on 2026-11-12 with the bundled mug, a person reference, and a lifestyle image. The scene is only a setting/light/prop reference; the prompt says not to copy its subject.

## Source images and request boundaries

- Originals are copied byte for byte and never sent.
- The working copy is normalised to WebP with the long edge at most 2048 pixels, quality 88, EXIF orientation applied, and metadata stripped.
- Edits send exactly one image. Create may send zero images, one product image (a saved Product, a library image, or an uploaded file), plus an optional person reference. The Image Generator can send a product and a person together; that path is a one-image edit request with the product first and the person second.
- A create request can send up to three references: one product, one person, and one scene. Edits send one or two images depending on the change and whether a scene is attached.
- The app user id for the API `user` field is a random installation id, not an email address.
- The prompt is assembled in `src/shared/prompts/guards.ts`. The reference guard is appended before the palette clause. If the palette clause does not fit under 2,000 characters it is dropped. The user's words are never truncated.

## Things not verified

The request and response shapes above were tested against `tests/fake-muse/server.ts`. They match the provider documentation available at build time. They were **not** run against a real Meta Muse key or invoice. The actual API may differ in any of these details:

- the `/models` key test response,
- the exact `output_format` echo,
- whether extra images beyond `n` are returned,
- invoice timing for a timed-out request,
- whether 429 uses `Retry-After`,
- whether any undocumented moderation field is required,
- the model's treatment of the reference guard.

A real-key check should record the HTTP status, headers, response keys, returned count, and invoice line. No response body containing the key should be copied into a report.
